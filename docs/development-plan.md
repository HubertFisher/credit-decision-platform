# План разработки Credit Decision Platform

**Статус:** рабочий план; предметные изменения начинаются после согласования соответствующих решений [дизайна](design.md).

## Как работаем

Оценка — 16 этапов примерно на 18–30 недель при 6–10 часах в неделю; это ориентир, не дедлайн. Этап может занять несколько занятий. На каждом: объяснение → пользовательская реализация → тестирование → review diff → самостоятельное объяснение → небольшой коммит. Агент не пишет код вместо пользователя без отдельной просьбы. Ни один этап не начинается до согласования документа.

На этапах 4–7 backend доступен только локально; authentication не считается необязательной для итоговой demo. Contract tests для ownership дописываются с Security. Outbox вводится после освоения основной state machine, но перед финальной демонстрацией все переходы обязаны писать события в своей TX. История с ранних этапов не обязана задним числом публиковаться в Kafka; seed/demo data создаются заново после включения event pipeline.

## Критерии завершения каждого этапа

Шаблон завершения любого этапа: работающий happy path; негативный/граничный случай; тест важного инварианта; просмотр git diff; обновлённая документация; один содержательный коммит; пользователь может объяснить полный request → service → transaction → PostgreSQL путь. Если объяснение не получается, уменьшаем шаг.

## После завершения v1: переход к микросервисам

После работоспособного модульного монолита предусмотрен отдельный учебный цикл:

1. Выбрать границу выделения и оформить ADR с причиной разделения; возможный кандидат — скоринг.
2. Описать контракт задания и результата, владение данными, таймауты, повторы и обработку запоздавших результатов.
3. Выделить сервис с собственным хранилищем и независимой сборкой; заменить общую транзакцию между сервисами согласованным протоколом.
4. Проверить сквозной сценарий, отказ одного сервиса, дубликаты и восстановление после недоступности.
5. Сравнить результат с монолитом: сложность, задержки, эксплуатация и независимость изменений.

Критерий готовности — сервис развёртывается независимо, не обращается к чужим таблицам и сохраняет инварианты обработки заявки при сетевых сбоях. Каждый модуль не обязан становиться отдельным сервисом. Детальный дизайн разделения оформляется после v1 на основе работающей системы.

Полные требования и итоговые критерии v1 находятся в [дизайне целевой системы](design.md).
