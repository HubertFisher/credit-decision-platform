# Credit Decision Platform — план реализации

## Цель

План определяет порядок реализации [целевой системы](design.md) и проверяемый результат каждого этапа. Базовая архитектура — модульный монолит с PostgreSQL, асинхронным скорингом и доставкой событий через transactional outbox и Kafka.

Этапы выполняются по зависимостям. Изменения схемы оформляются новыми миграциями Flyway; существующее поведение legacy API сохраняется до предусмотренного перехода на `/api/v1`.

## 1. Сборка и тестовое окружение

- Java 21 и Maven Wrapper обеспечивают единый способ сборки.
- Unit-тесты калькулятора и сервиса работают без Docker и БД.
- Тест запуска контекста создаёт временный PostgreSQL 16 через Testcontainers и применяет Flyway V1–V3.
- Полный `clean verify` выполняется без `.env`, предварительно собранного `target` и переменных подключения к БД.
- Workflow GitHub Actions запускает ту же сборку без отдельного PostgreSQL service.
- README описывает отдельные требования для тестов и обычного запуска приложения.

## 2. Скоринг и модель данных

Этапы 2–3 отделяют вычисление риска от HTTP и хранения. Политика содержит версию, неизменяемый набор правил и checksum. Результат включает score, recommendation, reason codes и breakdown каждого правила.

Новая модель разделяет `LoanApplication`, `ScoringAssessment`, `CreditDecision`, задания и историю попыток. Финансовые входы после подачи неизменяемы. Переходы заявки ограничены state machine, а финальное решение существует максимум в одном экземпляре.

## 3. Приём и обработка заявок

Этапы 4–7 реализуют API и надёжную обработку:

- Приём заявки атомарно сохраняет заявку, задание, историю и квитанцию команды.
- Idempotency-Key защищает от повторного создания эффекта.
- Worker обрабатывает сохранённые задания с lease token и ограниченными retries.
- Просроченные задания восстанавливаются; поздний worker не может записать результат.
- REVIEW_REQUIRED обрабатывается через отдельную команду сотрудника с expectedVersion и reason.
- Отмена разрешена только до начала скоринга; технический retry доступен для PROCESSING_FAILED.

На этих этапах незавершённое API доступно только в локальном окружении. Доступ к внешнему demo открывается после внедрения авторизации на этапе 8.

## 4. Безопасность и интеграция

Этапы 8–10 добавляют проверку access token, роли CUSTOMER/REVIEWER/OPERATOR/AUDITOR и фильтрацию данных по владельцу. Чувствительные действия и чтения сотрудников попадают в аудит.

После внедрения outbox все переходы сохраняют события в той же транзакции, что и состояние заявки. Kafka relay допускает повторную доставку; consumer использует eventId и aggregateVersion для защиты от дублей и устаревших snapshots.

События переходов, выполненных до появления outbox, не публикуются задним числом. Интеграционные наборы данных создаются после включения полного event pipeline.

## 5. Эксплуатационная готовность

Этапы 11–15 проверяют работоспособность системы при нагрузке и сбоях:

- Метрики HTTP, jobs, review queue, outbox, consumer lag, БД и JVM.
- Сквозная трассировка и структурированные логи без секретов и финансовых входов.
- Алерты на зависшие задания, исчерпание retries, backlog, DLT и проблемы backup.
- CI с unit, PostgreSQL, Kafka, security и архитектурными проверками.
- Контейнерный запуск и раздельные конфигурации local, CI и demo.
- Инструкции безопасного retry, DLT replay, миграции, rollback и восстановления.
- Нагрузочный отчёт с конфигурацией среды, исходными результатами и проверкой целевых показателей.

## Критерии завершения этапа

- Реализовано предусмотренное поведение и сохранены существующие контракты либо оформлена их миграция.
- Проверены основной сценарий, ошибки и значимые граничные случаи.
- Бизнес-инварианты и соответствующие сценарии конкуренции защищены тестами.
- Сборка и требуемые проверки проходят в воспроизводимом окружении.
- Обновлены затронутые API-контракты, схема данных, ADR и эксплуатационные инструкции.

## Развитие после v1: выделение микросервисов

Модульные границы позволяют выделить скоринг в самостоятельный сервис при необходимости независимого масштабирования, релизов или изоляции отказов.

Требования к выделению:

1. ADR определяет границу ответственности и причину разделения.
2. Контракты задания и результата содержат идентификаторы заявки, попытки и версии policy.
3. Сервис владеет своим хранилищем и не обращается к таблицам другого сервиса.
4. Общая транзакция заменяется протоколом обмена с идемпотентностью, retries и обработкой запоздавших ответов.
5. Сквозные тесты подтверждают сохранение инвариантов при сетевых сбоях и независимых рестартах.

Критерий готовности — независимое развёртывание и владение данными при сохранении корректного жизненного цикла заявки. Остальные модули могут оставаться в основном приложении, если их границы не требуют отдельного сервиса.
